# ファイル入出力 API の選定基準

固定レコード長バイナリ ファイルや構造体配列の入出力で、`com_util` の `stdio` ラッパー API とメモリ マップド ファイル API のどちらを使うかを、実測に基づいて判断するための基準をまとめます。

測定方法は [ベンチマークの測定方法](benchmark-method.md) を参照してください。  
本書の表は `bench-io` の出力から転記したものです。CSV そのものは実行環境ごとに値が変わるため、リポジトリでは管理していません。

## 測定条件

| 項目 | 内容 |
|------|------|
| 環境 | Linux (WSL2)、Intel Xeon Gold 6254 3.10 GHz |
| ファイル システム | ext4 (`magic=0xef53`) |
| ページ キャッシュ | warm のみ |
| レコード サイズ | 64 バイト |
| ファイル サイズ | 4 KB / 64 KB / 1 MB / 16 MB / 256 MB |

本書の数値はすべて 1 レコードあたりの所要時間 (ナノ秒) の中央値です。  
値は環境に強く依存するため、傾向と桁を読み取る目的で使用し、絶対値をそのまま他環境へ持ち込まないでください。

Windows の測定は未実施です。実施後に本書の結論を見直します。

## 結論の要約

1. アタッチを保持したまま繰り返しアクセスできるなら、mmap がほぼすべてのパターンで優位である
2. 1 回開いて 1 回通すだけの逐次アクセスでは、mmap の優位はなく、`stdio` のブロック単位読み書きと同等かやや劣る
3. ランダム アクセス、特に read-modify-write では mmap が桁違いに速い
4. 単発参照や短命なオープンが支配的な用途では `stdio` が優位である
5. 書き込みをディスクへ確実に反映する要件があると、mmap のコストが大きく跳ね上がる

## 固定コスト (ファイル サイズに依存しない)

| 操作 | 所要時間 |
|------|----------|
| `com_util_fopen` → `com_util_fclose` | 約 1.8 μs |
| `com_util_mmap_attach` → `com_util_mmap_detach` | 約 6.1 ～ 6.8 μs |
| 上にロックの取得と解放を加えたもの | 約 9.0 ～ 9.6 μs |

アタッチは `fopen` の約 3.5 倍のコストがかかります。  
ファイル サイズによらずほぼ一定であるため、1 回のアタッチでどれだけの処理をこなすかが選定の分かれ目になります。

ロックの取得と解放は約 2.9 μs です。  
`com_util_mmap_get_rwlock()` を呼ばない限りロックは生成されないため、排他が不要な用途ではこのコストは発生しません。

## パターン別の比較

### 逐次読み取り (seq-read)

| ファイル サイズ | `stdio-rec` | `stdio-blk` | `mmap-each` | `mmap-once` |
|------|------|------|------|------|
| 4 KB | 55.3 | 42.3 | 205.0 | 0.6 |
| 64 KB | 21.6 | 7.3 | 18.6 | 0.8 |
| 1 MB | 20.5 | 5.2 | 6.3 | 1.3 |
| 16 MB | 23.4 | 7.0 | 8.1 | 2.8 |
| 256 MB | 25.8 | 9.7 | 9.9 | 5.3 |

Table: 逐次読み取りの 1 レコードあたり所要時間 (ns)

アタッチを毎回行う `mmap-each` は、1 MB 以上で `stdio-blk` とほぼ並びますが、上回ることはありません。  
一方、アタッチを保持する `mmap-once` はどのサイズでも `stdio-blk` の 2 ～ 68 倍高速です。  
小さいサイズで差が極端に開くのは、warm な状態ではマップ済み領域が CPU キャッシュに収まり、システム コールが一切発生しないためです。

レコード単位で読む `stdio-rec` はブロック単位の `stdio-blk` に対して 2 ～ 4 倍遅くなります。  
`stdio` を使う場合、逐次アクセスではブロック単位でまとめて読み書きしてください。

### ランダム読み取り (rand-read)

| ファイル サイズ | `stdio-rec` | `mmap-each` | `mmap-once` |
|------|------|------|------|
| 4 KB | 208.0 | 204.0 | 0.8 |
| 64 KB | 524.8 | 19.5 | 0.9 |
| 1 MB | 583.2 | 6.9 | 1.7 |
| 16 MB | 824.9 | 26.3 | 8.3 |
| 256 MB | 1177.8 | 310.1 | 28.2 |

Table: ランダム読み取りの 1 レコードあたり所要時間 (ns)

`stdio` はレコードごとに `com_util_fseek` を伴うため、CRT の先読みバッファーが機能せず、サイズが大きくなるほど不利になります。  
mmap はページ フォールト以外のオーバーヘッドがなく、`mmap-once` で 7 ～ 40 倍高速です。  
アタッチを毎回行う `mmap-each` でも、64 KB 以上では `stdio` を大きく上回ります。

### ランダム更新 (rand-update)

| ファイル サイズ | `stdio-rec` | `mmap-each` | `mmap-once` |
|------|------|------|------|
| 4 KB | 1375.3 | 230.5 | 1.1 |
| 64 KB | 1427.6 | 34.3 | 1.2 |
| 1 MB | 1451.7 | 22.9 | 2.1 |
| 16 MB | 1712.2 | 96.0 | 9.3 |
| 256 MB | 2237.1 | 1097.6 | 29.8 |

Table: ランダム更新の 1 レコードあたり所要時間 (ns)

`stdio` の read-modify-write は突出して遅く、`mmap-once` に対して 75 ～ 1250 倍の差がつきます。  
同一ストリームで読み取りと書き込みを交互に行うと、C 標準の規定により方向を切り替えるたびにバッファーの掃き出しと位置合わせが発生するためです。

**構造体配列に対するランダムな読み書きが処理の中心である場合、`stdio` は選択肢になりません。**

### 逐次書き込み (seq-write)

| ファイル サイズ | `stdio-rec` | `stdio-blk` | `mmap-each` | `mmap-once` |
|------|------|------|------|------|
| 4 KB | 64.5 | 49.5 | 221.6 | 2.5 |
| 64 KB | 29.6 | 11.9 | 36.7 | 3.3 |
| 1 MB | 27.3 | 10.3 | 24.2 | 3.4 |
| 16 MB | 32.6 | 14.0 | 26.9 | 4.9 |
| 256 MB | 39.7 | 22.7 | 30.6 | 8.3 |

Table: 逐次書き込みの 1 レコードあたり所要時間 (ns)

傾向は逐次読み取りと同じです。  
`stdio-blk` は `mmap-each` と同等以上で、`mmap-once` のみが明確に優位です。

### 単発参照 (point-lookup) とオープンのみ (open-close)

| API | point-lookup | open-close |
|-----|------|------|
| `stdio-rec` | 約 3.2 μs | 約 1.8 μs |
| `mmap-each` | 約 12.9 ～ 18.0 μs | 約 6.1 ～ 6.8 μs |
| `mmap-lock` | 約 16.3 ～ 21.0 μs | 約 9.0 ～ 9.6 μs |
| `mmap-once` | 約 6 ns | (対象外) |

Table: 単発参照とオープンのみの所要時間 (ファイル サイズによらずほぼ一定)

ファイルを開いて 1 レコード読んで閉じる用途では `stdio` が 4 ～ 6 倍高速です。  
mmap はアタッチの固定コストを 1 レコードで償却できません。

## 耐久性を要求した場合

`mmap-once+sync` (`com_util_mmap_flush` により `msync(MS_SYNC)` まで実行) は、`mmap-once` に対して次のコストが上乗せされます。

| ファイル サイズ | `mmap-once` | `mmap-once+sync` | 倍率 |
|------|------|------|------|
| 4 KB | 2.5 | 18815.5 | 約 7500 倍 |
| 64 KB | 3.3 | 1812.8 | 約 545 倍 |
| 1 MB | 3.4 | 323.9 | 約 94 倍 |
| 16 MB | 4.9 | 137.7 | 約 28 倍 |
| 256 MB | 8.3 | 71.2 | 約 9 倍 |

Table: 逐次書き込みでディスクへの反映を要求した場合の 1 レコードあたり所要時間 (ns)

小さいファイルほど不利になるのは、`msync` の呼び出しコストとディスクへの書き戻し待ちを、少数のレコードで割ることになるためです。

**`stdio-rec+sync` と `stdio-rec` にはほとんど差がありません。**

これは `com_util_fflush` が CRT のバッファーを OS へ渡すだけで、ディスクへの書き戻しまでは待たないためです。  
両者は耐久性の水準が異なるので、**`+sync` 同士の数値を直接比較してはいけません。**  
`stdio` で mmap と同等の耐久性を得るには、`fflush` に加えて `fsync` 相当の処理が必要ですが、`com_util` にはそのラッパーがありません。

## 判断手順

上から順に評価し、最初に当てはまった項目に従ってください。

1. **ネットワーク ファイル システム上のファイルか**  
   → `stdio` を使用します。`com_util_mmap_attach` の `@warning` のとおり、mmap はローカル ファイル システム専用です。

2. **ファイル サイズがアドレス空間に収まらないか、実行時まで確定しないか**  
   → `stdio` を使用します。現在の `com_util_mmap` は部分範囲マップに対応しておらず、ファイル全体を一度にマップします。

3. **追記によってファイルを伸長するか**  
   → `stdio` を使用します。既存ファイルを開いた時点のサイズがマップ サイズに固定されるため、mmap では追記できません。

4. **1 回のオープンで扱うレコード数が数十未満か (単発参照が中心か)**  
   → `stdio` を使用します。アタッチの固定コスト約 6 μs を償却できません。

5. **ランダム アクセス、特に read-modify-write が処理の中心か**  
   → mmap を使用します。`stdio` との差は 1 桁から 3 桁に達します。

6. **同じファイルへ繰り返しアクセスし、ハンドルを保持できるか**  
   → mmap を使用します。アタッチを保持すればすべてのパターンで優位です。

7. **1 回開いて全体を 1 度だけ通す逐次処理か**  
   → `stdio` のブロック単位読み書き (`com_util_fread` / `com_util_fwrite` を 64 KB 程度でまとめる) を使用します。  
   mmap にしても同等以上にはならず、実装は複雑になります。

8. **上のいずれにも当てはまらない**  
   → `stdio` のブロック単位読み書きを既定とします。性能が問題になった時点で本書の表と照らして mmap への切り替えを検討してください。

## プロセス間共有が要る場合

複数プロセスから同一ファイルを排他制御しながら読み書きする場合は mmap を選びます。  
`com_util_mmap_get_rwlock()` で得たプロセス横断リーダーライター ロックを、`com_util_interprocess_rwlock_lock_shared()` および `com_util_interprocess_rwlock_lock_exclusive()` と組み合わせて使用します。

`stdio` ラッパー API にはプロセス間の排他機構がありません。

ロックはアタッチ時ではなく `com_util_mmap_get_rwlock()` の初回呼び出し時に生成されます。  
排他が不要な場合はこの関数を呼ばないでください。約 2.9 μs のコストを回避できます。

## OS による差の注意点

Windows の測定はまだ実施していないため、以下は API の性質から想定される差です。実測後に更新します。

- Linux の `mmap` と Windows の `CreateFileMapping` + `MapViewOfFile` では、マップ生成に必要な呼び出し数が異なります。Windows はマッピング オブジェクトの生成とビューのマップが 2 段階に分かれるため、アタッチの固定コストは Linux より大きくなる可能性があります。
- `com_util_mmap_flush` は Linux では `msync(MS_SYNC)` のみですが、Windows では `FlushViewOfFile` に加えて `FlushFileBuffers` を呼びます。後者はファイル全体のバッファーを対象とするため、`+sync` 条件のコストは Linux より大きくなる可能性があります。
- ページ フォールトの処理コストは OS とハードウェアに依存します。ランダム アクセスでの mmap の優位が、どの程度 Windows でも成立するかは実測で確認する必要があります。

## 現在の com_util_mmap API の制限

判断手順で `stdio` を選ぶ根拠になっている制限です。将来 API が拡張されれば基準も変わります。

- 既存ファイルを開くと、その時点のファイル サイズが固定のマップ サイズになり、追記による伸長ができない
- 部分範囲マップ (オフセットと長さの指定) に対応していない
- マップ サイズが 0 の場合はアタッチが失敗する
- ネットワーク ファイル システム上ではプロセス間の一貫性が保証されない

## 測定していない条件

次の条件は測定範囲外です。結論を適用する際は注意してください。

- Windows での全条件
- ページ キャッシュを落とした状態 (cold)。WSL2 では測定できないため、ネイティブ Linux での実施が必要
- 1 GB を超えるファイル (`--huge` で測定可能)
- 複数プロセスからの同時アクセス下での性能
- HDD やネットワーク ストレージなど、ext4 以外のストレージ
- 64 バイト以外のレコード サイズ
