# コーディング規範チェック

このスキルは `docs/general/coding-guideline.md` の薄いラッパーです。
判定基準・grep 例・コード例は原典に集約されているため、本書では参照先のみを示します。

## 適用範囲

- 主対象: `app/` 配下の C / C++ コード
- 前提とする言語標準は C17 / C++17 (`framework/makefw/makefiles/_flags.mk` の `C_STANDARD` / `CXX_STANDARD` の既定値)。C23 固有の機能は使わない
- 変更ファイル内の関数全てに適用する (関数単位の部分適用は避ける)
- 大規模な const 化リファクタリングは「1 commit = 1 ヘッダー (カテゴリ)」単位で進める  
  (詳細は原典「関数引数の const 付与と Doxygen 方向タグ」の「適用範囲と作業の進め方」)

## チェック項目 (原典のどの節を見るか)

1. **命名規則**
    - スコープ (公開 / ライブラリ内共有 / ファイル内 / 関数内ローカル) をヘッダーの配置と `static` の有無で判定する
    - 変数の `s_` / `g_` はリンケージ、ライブラリ接頭辞はリンカー名前空間、`_internal_` は公開境界を表す
    - 公開の関数・型は `<lib>_`、ライブラリ内共有の関数・型は `<lib>_internal_`。`static` 関数にはどちらも付けない
    - ファイル内共有変数は `s_`、ライブラリ内共有変数は `g_<lib>_internal_`、公開共有変数は `g_<lib>_` (必要最低限に厳選)
    - ヘッダー ファイル名の `_internal` は同名の公開ヘッダーがあるときだけ。シンボル規則とは付与条件が異なる
    - `_t` サフィックス、アンダースコア始まり、ユーザー定義識別子中の連続 `__` は、規格が処理系用に予約しているため使用しない (C++ 混在を含む)
    - 関数ポインター typedef のサフィックスは `_fn` に統一する。匿名 enum / struct の typedef は作らない
    - → 原典「命名規則」を参照

2. **整数型の選択**
    - 「値の意味に対応する型 → 幅に意味があるか → それ以外は `int`」の 3 段判定で型を選ぶ
    - 幅に意味がある値 (外部レイアウト、規格が定める計算値、OS API 境界) は固定幅型。それ以外に固定幅型を使わない
    - バイト列そのものを扱うバッファーの要素型は `uint8_t`
    - 真偽値は、公開ヘッダー (`include/`) では `int` の 0 / 非 0。`include_internal/` と `.c` では `bool` 可
    - 境界で `int` → `bool` は `(n != 0)` を明示。`bool` の記憶域へ `memcpy` / `fread` / 共用体 / ポインター キャストで書き込まない
    - → 原典「整数型の選択」「真偽値の型」を参照

3. **整数演算の安全性**
    - 符号付きと符号なしを直接比較しない。比較する場合は負値を先に排除してから同じ符号性へそろえる
    - 縮小変換と符号変換の明示キャストは、直前の範囲検査、または検査不要の理由コメントのいずれか必須
    - `size_t` の減算は、減算の前に大小関係を検査する
    - 符号付き整数の加減乗算は演算の前に上限・下限との関係を検査する (事後検査は不可)
    - 符号なしの意図的な回り込みにはコメントを残す。意図しない回り込みは範囲検査で防ぐ
    - 狭い型どうしの演算は整数昇格に注意し、必要なら演算前に広い型へ広げる
    - 確保サイズの乗算と外部文字列解析は既存規定 / com_util API へ委譲する
    - → 原典「整数演算の安全性」を参照。com_util 利用時は com_util 側の同名節も参照

4. **構造体のパディングと予約フィールド**
    - `pad` はアラインメントの穴埋め、`reserved` は将来のメンバー追加用。用途で名前を使い分ける
    - 予約フィールドは外部レイアウトが固定される構造体にのみ置く。内部構造体には置かない
    - `uint8_t reserved[16]` のように、要素数を直値のリテラルで書く。マクロ定数、`sizeof` 式、`enum` 定数は使わない
    - 空の `[]` は柔軟配列メンバーになるため使わない
    - 予約領域の先頭オフセットと構造体全体のサイズを、いずれも 8 の倍数に固定する (切り出す型の判断を不要にし、`-Wpadded` も同時に回避する)
    - 予約フィールドは `static_assert` で `sizeof` / `offsetof` を固定する。`pad` には `static_assert` を求めない
    - `pad` / `reserved` を持つ構造体は、いずれもゼロ初期化してから使用する (未初期化バイトの外部流出を防ぐ)
    - → 原典「構造体のパディングと予約フィールド」を参照

5. **関数引数の異常入力対応**
    - 概念的に正値のみ想定する引数の `int` 採用、負値挙動の仕様明記
    - NULL 検査の義務はヘッダーの配置で決まる。`include/` と `include_internal/` で宣言する関数は必須、`static` 関数は呼び出し側の責務
    - 判定は名前の `_internal_` の有無ではなくヘッダー配置で行う (既存コードは接頭辞が未移行)
    - 省略可能な出力引数 (エラー詳細の受け皿など) は対象外。NULL 許容であることを Doxygen に明記する
    - Doxygen は引数説明に「NULL を渡してはなりません。」、`@return` に返るエラー コードを書く
    - → 原典「関数引数の異常入力対応」を参照

6. **異常状態の検出とプロセス終了**
    - `assert` (`<assert.h>`) を使用しない。異常状態は引数検査で検出し結果コードで返す
    - 既定構成 `RelWithDebInfo` は `NDEBUG` を定義するため、`assert` は製品でもテストでも評価されない
    - コンパイル時条件は `static_assert` (`NDEBUG` 非依存のため対象外)
    - `abort()` はプロセス継続が危険な場合に限る。`assert` 経由でなく直接呼び、直前に原因を記録する
    - 引数不正・外部入力不正・I/O やメモリ確保の失敗・回復可能な失敗には使わない
    - → 原典「異常状態の検出とプロセス終了」を参照

7. **動的メモリの確保と解放**
    - 確保直後に NULL を検査する。確保失敗は結果コードで返し `abort()` しない
    - 確保サイズは `sizeof(*p)` 形。構造体メンバー宛も `sizeof(*obj->member)`。メンバー名・変数名が存在しない場合のみ型名を許容
    - 確保関数の戻り値は代入先の型へキャストする (型の食い違いを `-Wincompatible-pointer-types` で検出するため)
    - 要素数を伴う確保は `calloc(count, size)`。`malloc(count * size)` は使用しない
    - 長さ 0 の確保を行わない。要素数 0 は確保の前に分岐する
    - `realloc` は別変数で受け、NULL 検査後に元のポインターへ代入する
    - 解放後もスコープに残るポインター (構造体メンバー、外部リンケージ変数) には `free` の直後に NULL を代入する
    - 確保した領域を返す API は、解放責任と対になる解放関数を Doxygen の本文に書く
    - → 原典「動的メモリの確保と解放」を参照。com_util 利用時は com_util 側の「メモリ確保の代替」に従う

8. **エラー処理と戻り値規約**
    - 結果コードはライブラリ単位の共通 `#define` 群に統一 (成功 `{PREFIX}_OK` = 0、エラーは負値、-1 はその他のエラー)
    - 判定はコード名との比較を正とし、数値リテラル比較・三値規約・逆向き規約を使用しない
    - 真偽の答えは `int *xxx_out` の出力引数、戻り値は結果コード
    - 元 API 規約を保存する互換ラッパー層は適用対象外 (範囲は各ライブラリのドキュメントに従う)
    - → 原典「エラー処理と戻り値規約」を参照。各 app の特化事項があればそれに従う

9. **変数宣言位置と命令文の関係**
    - C17 スタイルでの宣言位置、`for` ループ変数のスコープ限定
    - 結果コード: API 一時受けは `ret` (別名 `rc` / `rtc`、原則初期化なし・使い回し可)、自関数が返す結果コード蓄積は `result` (初期化可)。単純透過は `return ret;` のみでよい
    - 結果コード以外の return に `ret` / `rc` / `rtc` / `result` を使わない。`err` / `status` や呼び出しごとの長い名前は使わない。`rc` / `rtc` は `ret` への統一を勧めてよいが修正非必須
    - `ret` は関数先頭で初期化子なしに宣言。初回呼び出しが宣言を兼ねる `int ret = func();` は避ける
    - → 原典「関数内ローカル変数」「変数宣言位置と命令文の関係」を参照

10. **式の括弧**
    - 種類の異なる演算子を混在させる場合は結合のまとまりを括弧で明示する。業界一般の規約より広く括弧を求める
    - 比較と算術、比較とビット演算・シフト、`&&` と `||` の混在、ビット演算子どうし、シフトと算術、単項 `!` の対象が 2 項式
    - 同種の演算子だけの式には付けない (`a + b + c` に括弧を重ねない)
    - `-Wparentheses` は一部しか検出しない (比較と算術の混在は警告されない)
    - → 原典「式の括弧」を参照

11. **関数引数の const 付与と Doxygen 方向タグ**
    - 意味的方向 `[in]` / `[out]` / `[in,out]` の確定、ポインター / 値渡しでの const 付与判定、  
      opaque handle / 同期プリミティブ / `FILE *` は常に `[in]`、mock 追従
    - 機械的フィルターの grep 例、典型誤りパターン、模範例ファイル、検証コマンドはすべて原典に記載
    - → 原典「関数引数の const 付与と Doxygen 方向タグ」の各下位節を参照

12. **宣言と定義での修飾子・マクロの配置**
    - エクスポート / 呼び出し規約マクロ (`EXAMPLE_EXPORT` / `EXAMPLE_API` 等) は宣言のみ、定義側には付けない
    - 値渡し引数の top-level const は定義側のみ、ポインター参照先 const は宣言・定義の両方
    - → 原典「宣言と定義の関係」を参照

13. **Doxygen コメントのプレースホルダー表記**
    - プレースホルダーは `<...>` ではなく `{...}` を使う (doxybook2 が XML タグと誤認するため)
    - 検証は `doxy*.warn` の「Unsupported xml/html tag」で行う
    - → 原典「Doxygen コメントのプレースホルダー表記」を参照

14. **API 設計における概念の分離**
    - 用途が異なる属性 (名前 / 識別番号、インスタンス / 出力先) は別フィールド・別 setter にし、getter も用意する
    - プロセス間排他とプロセス内排他を区別する
    - → 原典「API 設計における概念の分離」を参照

15. **各 app の特化事項**
    - プラットフォーム抽象化、標準時刻型、共通結果コードの具体運用など、app 固有の規則は各 app のドキュメントに従う
    - → 対象 app の `docs/` と `AGENTS.md` を参照

16. **Doxygen コード例内のコメント形式**
    - `@code` 内のコメントは `//` のみ。`/* */` は外側のドキュメント コメントを早期終端させる
    - → 原典「Doxygen コード例内のコメント形式」を参照

17. **制御構造の制限**
    - `goto` は関数末尾の解放ラベルへの前方ジャンプのみ許容。後方ジャンプ、条件分岐の代用、ブロック内への飛び込みは不可
    - 解放対象が 1 つ以下なら `goto` を使わず早期 return。ラベル名は `out_free_buffer` のように解放対象を表し、連番にしない
    - 三項演算子は使用しない。代替は `if` / `else` 文、または定数テーブル引き
    - → 原典「制御構造の制限」を参照

## 作業の進め方

1. 変更対象のヘッダー / impl の関数シグネチャを列挙する
2. 上記 17 項目について、原典の該当節を読みながら判定する
3. 判定結果を impl とヘッダー両方に反映する
4. 必要に応じて mock を追従する (原典「mock 追従」)
5. 原典「検証」節のコマンドで局所ビルド・テスト・Doxygen 警告を確認する

## 確認項目

- スコープごとの接頭辞と記法が命名規則に沿っているか (`static` 関数への接頭辞禁止、`static` 変数の `s_`、公開の `<lib>_` / `g_<lib>_`、ライブラリ内共有の `<lib>_internal_` / `g_<lib>_internal_`)
- 公開ヘッダーに `<lib>_internal_` が混入していないか。`include_internal/` の関数・型・外部リンケージ変数に公開境界マーカーがあるか
- 公開共有変数が必要最低限に厳選され、可能な限り `const` か。変更可能なプロセス大域状態を公開していないか
- ヘッダー ファイル名の `_internal` が「同名の公開ヘッダーがあるときだけ」になっているか
- `_t` サフィックス、アンダースコア始まり、ユーザー定義識別子中の連続 `__` を新設していないか。例外とした箇所には理由コメントがあるか。処理系マクロの参照は対象外
- 関数ポインター typedef が `_fn` サフィックスになっているか。匿名 enum / struct の typedef を作っていないか
- 整数型の 3 段判定に沿っているか。幅に意味がない値へ固定幅型を使っていないか。幅が意味を持つことが型宣言から自明でない箇所には理由コメントがあるか
- 公開ヘッダー (`include/`) に `bool` が現れていないか。真偽値が `int` の 0 / 非 0 になっているか
- レイアウトが外部との契約になっている構造体のメンバーに `bool` を使っていないか (`include_internal/` でも不可)
- 真偽値を `int` で表す箇所が、`is_` / `has_` / `_out` 直前の語で真偽と読み取れる名前になっているか
- 符号付きと符号なしを直接比較していないか。比較する場合に負値排除と符号性の揃えがあるか
- 縮小変換・符号変換の明示キャストに、直前の範囲検査または理由コメントがあるか
- `size_t` の減算の前に大小関係を検査しているか
- 符号付き加減乗算に演算前の範囲検査があるか (事後検査だけで済ませていないか)
- 意図的な符号なし回り込みにコメントがあるか。意図しない回り込みの経路がないか
- 狭い型どうしの演算で整数昇格による桁あふれを避けているか
- 確保サイズの乗算を自前で行っていないか。外部文字列解析を `com_util_parse_*` 等へ委譲しているか
- `pad` と `reserved` を用途どおりに使い分けているか。予約フィールドが `uint8_t` 配列で、要素数が直値のリテラル (マクロ定数や `sizeof` 式ではない) になっているか
- 予約フィールドが構造体末尾にあり、先頭オフセットと全体サイズがいずれも 8 の倍数か。`static_assert` が伴っているか
- `pad` / `reserved` を持つ構造体がゼロ初期化されてから使用されているか
- 負値のガードと Doxygen 仕様明記が揃っているか
- `include/` / `include_internal/` で宣言する関数が、ポインター引数の NULL を本体先頭で検査しているか。`static` 関数に不要な検査を入れていないか
- 出力引数が「省略可能で NULL 許容」か「必須で NULL 検査」のいずれかに定まり、Doxygen に明記されているか
- `assert` / `<assert.h>` を使用していないか。コンパイル時条件に `static_assert` を使っているか
- `abort()` の呼び出しが、プロセス継続が危険な場合に限られているか。回復可能な失敗に使っていないか
- `abort()` の直前に原因を特定できる記録があるか。プロセスを終了させうる関数の Doxygen にその旨が書かれているか
- 確保関数の戻り値を、呼び出した直後に NULL 検査しているか。確保失敗で `abort()` していないか
- 確保サイズが `sizeof(*p)` 形になっているか。型名を書いている場合、代入先にメンバー名・変数名が存在しないケースに該当するか
- 確保関数の戻り値を代入先の型へキャストしているか
- 要素数を伴う確保が `calloc(count, size)` になっているか。`malloc(count * size)` の形が残っていないか
- 長さ 0 の確保を呼び出す経路がないか。要素数 0 を確保の前に分岐しているか
- `realloc` の戻り値を元のポインターへ直接代入していないか。別変数で受けて NULL 検査後に代入しているか
- 解放後もスコープに残るポインターへ `free` の直後に NULL を代入しているか。関数を抜ける直前のローカル変数に不要な代入をしていないか
- `free(NULL)` が無害であることを前提に、解放前の冗長な NULL 検査を入れていないか
- 確保した領域を返す API の Doxygen 本文に、解放責任と対になる解放関数が書かれているか。`@return` にだけ書いて本文にない状態になっていないか
- 破棄関数を呼ぶ側が NULL ガードを行っているか (破棄関数側が NULL を受け入れることを理由に省略していないか)
- 結果コードがライブラリ共通の `#define` 群 (成功 0 / エラー負値) に統一され、数値リテラル比較・三値規約・逆向き規約になっていないか
- 変数宣言位置が利用箇所に近く、可読性を損ねていないか
- `ret` (または別名の `rc` / `rtc`) が関数先頭で初期化子なしに宣言され、初回呼び出しが宣言を兼ねる形になっていないか
- 自関数の結果コード蓄積に `result` を使う場合、計算結果など非結果コードに `result` を流用していないか。単純透過で不要な `result` を増やしていないか
- 種類の異なる演算子の混在に括弧が付いているか (比較と算術、比較とビット演算、`&&` と `||` の混在など)。同種の演算子だけの式に冗長な括弧を重ねていないか
- ポインター引数の const 付与判定が impl と整合しているか
- Doxygen `@param[in/out/in,out]` が impl の挙動と一致しているか
